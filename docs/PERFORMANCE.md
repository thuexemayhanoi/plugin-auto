# Performance

All numbers below are **measured**, not estimated, with `tests/bench/run-bench.sh <N>` on
2026-10-23. Raw results: [`docs/evidence/bench-10.json`](evidence/bench-10.json),
[`bench-100.json`](evidence/bench-100.json), [`bench-1000.json`](evidence/bench-1000.json).

* **Machine:** sandbox container, 4 vCPU, 16 GB RAM, PHP 8.3.6 CLI, MariaDB 10.11, WordPress 7.1.3
  with Polylang 3.9.1, PHP built-in web server (`php -S`, 4 workers) — slower than a tuned
  PHP-FPM/OPcache production stack, so treat the numbers as conservative relative values.
* **Data:** SYNTHETIC BENCHMARK FIXTURE generated by `tests/bench/generate.php` (≈ 70% Vietnamese,
  30% English, 6 categories, template-based titles/paragraphs, some internal links). It is
  template-heavy on purpose, so it produces many more overlap/QA findings per page than a
  hand-written site would.
* **Tier:** lexical (no model). Embeddings are computed outside PHP (browser or private worker).

## Independent audit (1.0.0-beta.3): large sites

Measured on the same machine; details in [QA-AUDIT-REPORT.md](QA-AUDIT-REPORT.md) §6 and
[`audit-bench-20000-partial.json`](evidence/audit-bench-20000-partial.json),
[`audit-cluster-step-20000.json`](evidence/audit-cluster-step-20000.json),
[`bench-1000-beta3.json`](evidence/bench-1000-beta3.json),
[`audit-neardup-1500.json`](evidence/audit-neardup-1500.json).

* **Corrected claim:** before 1.0.0-beta.3, a background tick did **not** always stay within its
  budget. Batches were fixed at 25 objects, and the budget was only checked between batches. On
  20,000 posts, one tick with a 20 s budget took 68 s. Batches are now sized from the measured time
  per item: 20.5–22.1 s per 20 s tick.
* **Cluster step**, 20,000 posts:
  * before: one step, 159 s, 759 MB peak, fatal under a 256 MB WP-Cron request;
  * now: 10.7 s, 156 MB, identical results.
* **Still slow at 20,000 posts (not fixed; needs a df-statistics redesign):** the pairs phase takes
  0.52 s per document in one CLI process (≈ 3 h in total) and ≈ 5 s per document in WP-Cron ticks,
  where every request starts with cold document-frequency caches. At 6,000 posts it is 0.17–0.26 s
  per document. The reference blog has ≈ 1,083 URLs.
* **1,000 posts (beta.3):** 94.2 s for a full CLI run, 131 MB.
* **1,500 near-duplicate posts:** 295 s, 167 MB, 37,362 overlap pairs (24.9 per post; candidate
  search is bounded, not all-pairs).

## Analysis throughput and memory

| Posts | Documents (posts + terms) | One background tick (budget 20 s) | Full inventory + analysis (one CLI process) | Peak RSS of that process | Plugin tables |
| ---: | ---: | --- | ---: | ---: | ---: |
| 10 | 20 | 0.18 s, 57 MB | 0.7 s | 89 MB | 1.1 MB |
| 100 | 110 | 1.9 s, 57 MB | 10.0 s | 91 MB | 7.4 MB |
| 1,000 | 1,010 | 11.9 s, 63 MB | 207.7 s (≈ 0.21 s/post) | 125 MB | 62.6 MB |

Index sizes at 1,000 posts: 201,564 postings, 3,014 chunks, 995 resolved links, 5,000 related
rows, 14,894 findings.

What this means in practice:

* Background work stays within the per-tick time budget (default 20 s, configurable 3–50 s); since
  1.0.0-beta.3 batches are sized from the measured time per object (at most 25 by default); a WP-Cron tick stays well under typical PHP limits
  (`max_execution_time` 30 s) and memory limits (≥ 64 MB was enough; WordPress' default admin
  limit is 256 MB).
* A 1,000-post site is fully analysed in ≈ 3.5 minutes of background work. Time per post grows
  mildly with site size (0.10 s → 0.21 s per post from 100 to 1,000) because candidate retrieval
  touches larger posting lists; it is not all-pairs.
* Re-analysis after edits is incremental: only changed documents (content hash) are re-indexed
  and re-analysed.

## REST API latency (HTTP, Application Password, 20 sequential requests each)

| Endpoint | 10 posts median / p95 | 100 posts | 1,000 posts |
| --- | --- | --- | --- |
| `GET /status` | 34 / 49 ms | 45 / 84 ms | 64 / 82 ms |
| `GET /inventory?limit=20` | 32 / 39 ms | 48 / 62 ms | 217 / 246 ms |
| `GET /inventory?limit=20&search=xe` | 30 / 40 ms | 39 / 48 ms | 178 / 225 ms |
| `GET /analysis?url=…` | 31 / 53 ms | 30 / 36 ms | 60 / 83 ms |
| `GET /suggestions/links?limit=20` | 28 / 32 ms | 30 / 35 ms | 46 / 55 ms |
| `GET /cannibalization?limit=20` | 28 / 32 ms | 29 / 34 ms | 51 / 62 ms |
| `GET /qa?limit=20` | 26 / 28 ms | 28 / 31 ms | 37 / 46 ms |

`/inventory` is the slowest at 1,000 posts because each matrix row aggregates counts (links,
findings, QA) per document; it is paginated (≤ 100 rows) so it stays bounded. This is the first
candidate for optimisation (denormalised counters) in a later release.

The admin pages rendered in 0.4–0.9 s each in the browser test (WordPress 7.1.3, 38 documents,
including WordPress' own admin chrome).

## Front end

With related-content output **off** (default) the plugin adds nothing to public pages; the HTML
was byte-identical before and after activation and after a full analysis
(`tests/e2e/smoke-zip.sh`). With output on, the shortcode/block renders a cached, precomputed list
(object cache group `sseo_related`) with no extra requests (verified: all front-end requests
same-origin, no model, worker or admin script).

## Real Qwen3-Embedding-0.6B inference (measured in GitHub Actions)

Runner: GitHub-hosted `ubuntu-latest` (4 vCPU, 16 GB RAM, no GPU), workflow
"Real Qwen3-Embedding-0.6B". Texts are the labelled fixture documents (titles + paragraphs, up to
512 tokens) and the model-card self-test sentences.

| Path | Precision | Measured |
| --- | --- | --- |
| Download of the pinned files from huggingface.co (runner network) + SHA-256 | q4f16 (567 MB) | ≈ 3 s download + verification |
| Browser worker, Chromium headless, **WASM, 1 thread** (page not cross-origin isolated) | q4f16 | first load incl. download + verification + runtime init 8.2 s; reload from the verified browser cache 4.2 s (no download); self-test + 8 texts (4 of them long) ≈ 51 s → **several seconds per long text on CPU** |
| Browser worker, WASM, 1 thread | fp16 (1.2 GB) | self-test + 8 texts ≈ 63 s |
| Browser worker, WebGPU through SwiftShader (software adapter, no GPU) | q4 | runs and passes the self-test, but a software GPU is not representative; **real GPU speed not measured** |
| Python private worker, ONNX Runtime CPU (4 threads), one text at a time in batches of 4 | q4f16 | 0.39–0.77 s per fixture document; 89 queued chunks embedded and stored over REST in 80 s (incl. model load and self-test) |
| Same | fp16 / fp32 | ≈ 0.39–1.24 s per document (fp16 ≈ fp32 on CPU) |

Practical consequence: on a CPU-only browser, embedding a 1,000-post site (several chunks per
post) takes hours; a desktop browser with a real WebGPU GPU or the private worker is the
practical choice for large sites. Lexical analysis never waits for embeddings.

## Copy of the real blog (1,083 URLs, measured in GitHub Actions)

Read-only pilot on a disposable copy of blog.rentbikehanoi.com's public content (TEST-REPORT §7;
same 4-vCPU runner, WordPress 7.1.3 + Yoast SEO + the site's VI-EN plugin, PHP 8.3, MariaDB 10.11).
Real pages are much longer than the synthetic benchmark (average 2,139 words, 17,944 chunks).

| Step | Time |
| --- | ---: |
| Inventory of 1,083 documents | 49 s |
| Lexical analysis (all modules) | 642 s (≈ 0.6 s per document) |
| Embedding 3,201 queue items (summary + first 2 body chunks per page), private worker, q4f16, ONNX Runtime CPU 4 threads, over REST | 5,130 s (≈ 1.6 s per item, ≈ 85 min); run 2: 3,197 items in 4,944 s |
| Hybrid re-analysis with vectors | 651 s |

For the owner this means: the first full embedding of the blog takes about 1.5 hours on a 4-core
computer running the private worker (a desktop browser with a real GPU was not measured); after that
only new or edited pages are re-embedded and re-analysed (content hash).

## Tuning

* *Batch size* and *time budget per background tick* (Settings → Operations) bound each tick.
* *Candidates per page (BM25 top-k)* (Expert panel, default 15) bounds pair analysis.
* *Max documents* (default 5,000) caps how many documents the inventory holds. New objects beyond
  it are counted, not indexed; documents already stored keep being refreshed (nothing is deleted
  when the limit is lowered). The overview page and `GET /status` (`inventory_limit`) say when the
  limit was reached and how many objects in scope were left out. Raise it for larger sites (the
  6,000-post benchmark raises it to the post count).
* Large sites: run the initial analysis with `wp sseo start inventory --then-analyze --run` from
  WP-CLI (no request timeouts), then let incremental updates run in the background.
